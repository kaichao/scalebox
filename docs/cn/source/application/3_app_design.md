# 3. 应用设计

## 3.1 Scalebox应用程序

### 3.1.1 应用特点
- 面向数据密集型场景优化的容器化计算程序
- 依赖于Scalebox执行框架，通过事件驱动形式实现多节点分布式、并行计算
- 主要应用于天文计算场景，未来可应用于生物数据处理、数字电影制作、视频加工等高数据I/O场景

### 3.1.2 与传统MPI编程的比较

| 特性       | Scalebox           | 传统的MPI/Charm++        |
| -------   | ------------------  | -------------------------|
| 编程范式   | 消息驱动、过分解       | 进程通信、单程序多数据(SPMD) |
| 负载均衡   | 动态、自动化           | 多为主观、静态            |
| 容错机制   | 内置支持               | 要额外实现                |
| 可扩展性   | 流式驱动，支持极大规模并行 | 大规模时面临挑战  |
| 编程复杂度 | 高级抽象，较低         | 底层控制，较高            |

## 3.2 应用组成

### 3.2.1 模块组成
Scalebox应用程序由多个容器化封装的软件模块组成：

- **主路由模块**：应用的控制面模块，执行并行逻辑、读写应用状态、把任务分发给定制算法模块与公共基础模块，并组织模块协作
- **定制算法模块**：用户业务模块，以消息驱动形式，实现特定算法功能（算法逻辑）
- **公共基础模块**：
  - 文件传输：基于计算系统内置的ssh，支持跨节点的数据传输
  - 目录列表：辅助产生待处理文件

应用组成与核心概念的对应关系：主路由负责并行逻辑与应用状态；定制算法模块实现算法逻辑；公共基础模块提供传输、目录列表等通用能力。详见 {doc}`核心概念 <1_core_concepts>`。

### 3.2.2 应用定义文件
- **应用模板文件**：以YAML文件格式，定义应用所包含的各个模块的相关定义
- **参数定义文件**：以环境变量文件形式，定义应用模块文件中相关参数

## 3.3 应用设计原则

### 3.3.1 核心概念在设计中的落点

| 概念 | 设计时要回答的问题 | 落点 |
|---|---|---|
| 计算逻辑（算法逻辑 + 并行逻辑） | 大问题如何分解？模块内怎么算？模块间怎么协作？ | app.yaml 拓扑 + 主路由脚本 + header |
| 应用状态 | 需要记住什么？存在哪里？ | semaphore / variable / global + vtask |
| 主路由 | 谁执行并行逻辑？串行还是多实例？ | main-router 模块与脚本 |
| VTask | 是否需要粗粒度封装？流控/容错怎么做？ | vtask 管道 |

### 3.3.2 主路由执行并行逻辑、集中管理应用状态
- 主路由执行并行逻辑：任务分发、分组/排序、同步/汇聚、流控/准入；不处理具体业务算法。
- 应用状态由主路由集中读写，避免应用层并发冲突；平台 controld 在 vtask 等场景也会读写信号量。
- 默认单实例、逻辑串行；高负载可按模块分设 SLOT-BOUND 多实例，并发正确性由程序员保证。
- 详见 {doc}`核心概念 §1.5 <1_core_concepts>` 与 {doc}`主路由与应用状态 <../design/2_main_router_status>`。

### 3.3.3 算法模块无状态
- 算法模块实现算法逻辑；通过环境变量、任务头定义不同逻辑处理。
- 不持有应用状态；应用状态由主路由与平台存储承担。
- 尽可能在模块级实现任务幂等；跨模块幂等由 vtask 层保证。

### 3.3.4 按逻辑功能划分模块
- 细分模块支持流水线并行
- 按功能划分，提高复用性

### 3.3.5 节点本地计算模式
- 提升I/O带宽
- 减少中间存储量，可以生成部分结果，尽可能早生成最终结果
- 节点本地计算需要准入控制与跨模块同步；并行逻辑与应用状态在这些约束下协作。详见 {doc}`节点本地计算 <../design/4_node_local_compute>`。

### 3.3.6 复用标准模块
- 尽可能使用现有的标准模块
- 减少重复开发工作

## 3.5 应用设计模式

### 3.5.1 简单流水线模式
```
数据输入 → 处理模块 → 输出结果
```

特点：
- 单模块处理
- 适合简单计算任务
- 易于理解和调试

### 3.5.2 多级流水线模式
```
数据输入 → 预处理 → 计算 → 后处理 → 输出
```

特点：
- 多模块协作
- 数据逐步处理
- 支持复杂计算流程

### 3.5.3 并行流水线模式
```
       → 处理A →
输入 → 处理B → 合并 → 输出
       → 处理C →
```

特点：
- 模块级并行处理
- 提高处理效率
- 适合数据并行任务

### 3.5.4 混合并行模式
```
       → 并行A →
输入 → 串行处理 → 并行B → 输出
       → 并行C →
```

特点：
- 结合串行和并行
- 灵活的任务调度
- 适合复杂应用场景

### 3.5.5 跨集群模式
```
集群A: 数据生成 → 集群B: 数据处理 → 集群C: 结果分析
```

特点：
- 跨集群计算
- 异构集群支持
- 适合大规模分布式计算

## 3.6 应用设计最佳实践

### 3.6.1 模块划分原则
1. **单一职责**：每个模块只负责一个功能
2. **高内聚低耦合**：模块内部紧密相关，模块间松耦合
3. **可复用性**：设计通用模块，提高复用率
4. **可扩展性**：支持模块的动态添加和替换

### 3.6.2 数据流设计
1. **数据局部性**：优先使用本地存储，减少数据传输
2. **流水线并行**：合理安排模块顺序，最大化并行度
3. **批量处理**：合理设置批量大小，平衡延迟和吞吐量
4. **容错设计**：设置重试机制和错误处理

### 3.6.3 性能优化策略
1. **并行度设置**：根据数据量和计算资源合理设置并行度
2. **资源分配**：根据任务需求合理分配计算资源
3. **缓存策略**：合理使用缓存减少重复计算
4. **负载均衡**：确保各节点负载均衡，避免资源浪费

### 3.6.4 可维护性设计
1. **模块化设计**：功能模块化，便于维护和升级
2. **配置化管理**：通过配置文件管理应用，降低维护成本
3. **监控告警**：集成监控和告警机制，及时发现和解决问题
4. **文档完善**：提供详细的文档和使用说明

### 3.6.5 容错设计
1. **任务级重试**：按 `retry_rules` 配置退出码与重试次数，处理非逻辑错误。
2. **跨模块容错**：用 vtask 级联终止失败链并释放资源；vtask 层保证幂等与最终一致。
3. **故障隔离**：设置 `task_max_seconds` 与 `task_min_seconds`，避免死循环与故障 slot 干扰。
4. **可观测性**：用 `task show`、`vtask get`/`vtask list` 定位失败与卡点。

详见 {doc}`高级编程特性 <../design/7_advanced_features>` §7.1 与 {doc}`VTask 虚拟任务 <../design/3_vtask>`。

## 7.1 容错机制

模块运行错误通常分为两类：
- 逻辑错误：代码逻辑导致的结果错误；
- 非逻辑错误：外部软硬件环境异常导致的结果错误；通常在外部环境恢复后，重复多次运行，可解决；

非逻辑错发生有一定的概率，大规模数据处理中，非逻辑错的自动处理，将大大提升数据处理的效率及可靠性。

### 常见的外部运行环境异常
- 不稳定的硬件和基础软件
  - 网络设备链路的不稳定
  - 环境温度升高，导致计算节点暂时停止服务
  - 磁盘盘阵中介质不稳定，导致RAID暂时失效
  - 集群存储软件的临时性、可修复的bug
- 运行中的随机异常
  - 高负载导致核心存储响应延时增加
    - 可变延时（数秒~几分钟）
    - 暂时性不可写入
  - 高负载导致低概率的内存超分，应用内存不足
  - 系统高负载，不合适的调度策略，导致算法运行超时
- 数据异常
  - 异常输入数据
  - 前导处理软件的随机错误
  - 各类运行异常导致的数据不完整

### 非逻辑错的容错处理
- 系统异常的判断与定位
  - 读取/执行/回写的时间
  - 任务返回码
  - 系统监控的异常信息
- 异常任务的容错处理
  - 自动/人工


## 7.1.1 模块级容错
- 设置module的参数retry_rules。
按照算法代码对于非逻辑错的错误，设置主脚本不同的错误码。按返回错误码，在模块定义中设置自动重试，从而实现自动重试。

在Module定义中，设置```retry_rules```实现以上功能。

```
    retry_rules: "['91','92:3']"
```
在以上设置中，若返回码为91，则重试1次；若返回码为92，则重试3次。

返回码是模块运行的结果代码，模块运行出错的返回码就是错误码。

## 7.1.2 平台级故障及恢复

- slot启动运行出错，但运行task时很快出错，导致task运行时间短，单位时间内可完成多个task；
- module的max_tasks_per_minutes参数（取值>=3），在超出该参数时，将对应slot设置为'ERROR'，以免干扰其他task的正常等待；
- 再结合retry_rules，即可在有大量slot运行错的情况下，停止有问题的slot运行；
- 最后，可以再通过手工恢复。

## 7.2 准入控制机制

准入控制(Admission Control)

本地计算本地资源受限，需引入准入控制，避免本地节点超载。
对于复杂应用程序的本地计算，高级流控可大大简化流控逻辑，避免运行异常。

算法模块的流量控制，就是控制流式数据处理的进度，以免数据处理所需不可共享的核心计算资源（内存缓存、GPU显存、本地磁盘空间）超过本地资源的物理限额，导致计算过程中出现异常，包括异常退出、程序死锁等。

流量控制的实现机制是在消息处理前，通过模块的标准流控规则、自定义流控规则检查是否符合外部条件，若不符合，则在代码中显式调用sleep()，等待一段时间后再做检查。经过多次检查未果，则退出模块运行。

流控规则通过引入等待机制，降低了局部计算资源的利用率，但从整体上保证应用程序的顺利执行。
避免内存空间的峰值需求，以增加等待时间为代价，在低内存配置的机器上运行本地计算的应用。

流控分为slot级流控、node间并行同步流控。
流控支持模块运行的同步，以免系统资源受限而导致运行异常。

精准控制数据输出，若数据空间不满足，等待其他并行任务完成后释放资源，清理出空间，待空间容量满足要求后再继续运行。

### 7.2.3 vtask计数准入控制

启用vtask的模块，在task启动时将计数器自动减一，若计数器为0，则计数流控生效，新task不能运行。从实现上看，vtask机制设置了等待队列长度。

后续模块的消息处理完成后，在消息路由中自动恢复vtask计数器。也可对计数器手工操作，实现启停。

- 处理过程
  - 在模块入口处，检查信号量计数器，若小于等于0，表示无运行槽位，流控不通过；
  - 该给后续消息路由发送消息中，加上消息头```global_vtask / group_vtask / host_vtask```
  - 消息路由对该计数值自动减一，占用一个运行槽位。该操作自动完成，不需要编程控制；
  - vtask处理完成，则在对应消息路由中，通过信号量操作，对计数值加一，释放一个空槽位。

#### global_vtask
- 属性名：```global_vtask_size```，后续模块的等待队列长度。

- yaml应用文件解析时，生成对应信号量：```global-vtask-size_${mod_name}```，其初值为参数值。
  - mod_name为首模块名，模块通常运行在头节点上，仅有1个全局slot。

#### 按计算节点组的vtask数量流控
- 属性名：```group_vtask_size```，计算节点组上最多可运行vtask数量，表示最多可进入运行的vtask数量。

- yaml应用文件解析时，生成对应信号量：```group-vtasks-size_${mod_name}_${groupname}```，其初值为参数值。
  - mod_name为首模块名，首模块通常为头节点上运行的模块，全系统中仅有1个对应的slot
  - groupname为t_host表中对应的gid

#### 按计算节点的vtask数量流控
- 属性名：```host_vtask_size```，计算节点上最多可运行的vtask数量，表示节点上运行队列的长度。

- yaml应用文件解析时，生成对应信号量：```host-vtask-size_${mod_name}_${hostname}```，其初值为参数值。
  - mod_name为首模块名，首模块通常为HOST-BOUND，每节点上仅有1个slot
  - hostname为slot对应的hostname


### 7.2.4 节点组并行同步准入控制

## 7.2 超时设置（timeout）

由于代码的bug、数据错误等原因，可能导致算法模块进入死循环，一直占用slot运行，无法正常退出。

超时设置可以解决以上问题。通过设置module的```task_max_seconds```参数，在超出该时限后，该任务（task）会退出运行，返回错误码 124.

在封装脚本调用算法代码时，建议也在封装脚本中加入timeout的相关设置。若无此设置，外层脚本timeout，内层脚本还会运行结束，导致不确定的结果。
若算法代码名为run.py，则封装代码中对应部分可写成：
```sh
timeout ${TASK_TIMEOUT_SECONDS}s run.py $*
```


## 7.3 多GPU配置

单个计算节点可配置多个GPU加速卡。通常为每个GPU配置独立的slot，模块算法就不需要针对多GPU卡做并行优化，这样配置通常也更具高运行效率。
在这种场景下，不同GPU需要用不同的slot启动命令。
scalebox启动命令支持参数化配置。

参数化命令配置如下：

```
docker run -d --rm --network host --tmpfs=/work --device=/dev/kfd --device=/dev/dri --security-opt seccomp=unconfined --group-add video -e ROCR_VISIBLE_DEVICES={~n~} {{ENVS}} {{VOLUMES}} {{IMAGE}}

docker run -d --rm --network=host --tmpfs=/work --device=/dev/kfd --device=/dev/dri/card{~n%2~} --device=/dev/dri/renderD{~n%2+128~} --security-opt seccomp=unconfined --group-add video --cap-add=SYS_PTRACE {{ENVS}} {{VOLUMES}} {{IMAGE}}
```

其中， ```{~ ~}```中间的为运行时表达式，其中n为节点上slot编号（从0开始）。在启动slot前，动态解析为对应值。

## 7.9 slot自动扩缩容

### 7.9.1 概述

Slot 自动扩缩容是 ScaleBox 平台的核心特性之一，用于根据资源使用情况自动调整任务执行槽（slot）的数量。系统通过监控主机资源使用率，智能决策何时扩容（增加slot）或缩容（减少slot），以优化资源利用率和任务执行效率。

### 7.9.2 功能特性

#### 核心功能
- **自动监控**：定期检查主机资源使用情况
- **智能决策**：基于使用率阈值自动决定扩容/缩容
- **双重策略**：支持资源紧张扩容和容量不足扩容
- **安全保护**：防止过度扩容和过度缩容
- **冷却机制**：避免频繁调整，确保系统稳定

#### 扩缩容场景
1. **资源紧张扩容**：当资源使用率超过阈值时扩容
2. **容量不足扩容**：当slot数量远低于最大容量时扩容
3. **资源闲置缩容**：当资源使用率过低时缩容
4. **超量运行缩容**：当slot数量超过物理容量时强制缩容

### 7.9.3 实现原理

#### 系统架构
```
+----------------+     +----------------+     +----------------+
|   资源监控模块   | --> |   决策算法模块   | --> |   Slot调整模块  |
+----------------+     +----------------+     +----------------+
        |                       |                       |
        v                       v                       v
+----------------+     +----------------+     +----------------+
| 收集主机资源数据 |     | 计算扩缩容决策  |     |  执行slot调整   |
+----------------+     +----------------+     +----------------+
```

#### 数据流
1. **资源收集**：从数据库获取主机总资源、已使用资源和slot需求
2. **指标计算**：计算最大可用slot数量和资源使用率
3. **决策判断**：基于阈值判断是否需要调整
4. **执行调整**：通过slot管理接口调整slot数量

### 7.9.4 算法说明

#### 核心算法流程

```go
// 五步算法流程
1. 计算最大可用slot数量
2. 计算最大资源使用率
3. 检查是否需要扩容
4. 检查是否需要缩容
5. 返回调整决策
```

#### 详细算法步骤

##### 1. 计算最大可用slot数量
- 获取总资源、已使用资源、slot需求的交集
- 对每个共同指标：`可用slot = (总资源 - 已使用资源) / slot需求`
- 取所有指标中的最小值作为最大可用slot数量
- 应用配置限制（最小/最大slot数量）

##### 2. 计算最大资源使用率
- 对每个共同指标：`使用率 = 已使用资源 / 总资源`
- 取所有指标中的最大值作为决策依据

##### 3. 扩容检查（双重条件）
- **条件A：资源紧张扩容**
  - 触发：`使用率 > 扩容阈值`
  - 目标：缓解资源压力
- **条件B：容量不足扩容**
  - 触发：`当前slot数量 < 最大可用slot数量 × 容量阈值`
  - 目标：充分利用可用容量

##### 4. 缩容检查（双重条件）
- **条件A：资源闲置缩容**
  - 触发：`使用率 < 缩容阈值`
  - 目标：减少资源浪费
- **条件B：超量运行缩容**
  - 触发：`当前slot数量 > 最大可用slot数量`
  - 目标：强制缩容到物理容量内

##### 5. 调整数量计算
- **扩容数量**：`min(最大可用 - 当前, 扩容步长)`
- **缩容数量**：`min(当前 - 目标, 缩容步长)`
  - 资源闲置缩容：目标 = 最小slot数量
  - 超量运行缩容：目标 = 最大可用slot数量

| 参数名 | 类型 | 默认值 | 说明 |

| 参数名 | 类型 | 默认值 | 说明 |

### 9.9.6 资源指标要求

该项配置位于主机配置的metrics中，由外部监控系统定时更新。

```json
{
  "slot_req.compute_units": "1",
  "slot_req.memory_mb": "256",
  "slot_req.disk_gb": "10"
}
```
该项配置位于模块配置的parameters中。

#### 指标要求
1. **指标一致性**：三类指标需要有相同的key前缀（去掉前缀后）
2. **数值类型**：所有值必须是数值类型（整数或浮点数）
3. **单位一致**：相同指标的单位必须一致

### 9.9.7 使用示例

#### 场景1：正常扩容
```
初始状态：当前slot=3，最大可用slot=10，使用率=90%
配置：扩容阈值=80%，容量阈值=80%

决策过程：
1. 使用率90% > 80% → 触发资源紧张扩容
2. 当前3 < 10×80%=8 → 触发容量不足扩容
3. 可扩容数量：min(10-3=7, 扩容步长=2) = 2
结果：扩容2个slot
```

#### 场景2：正常缩容
```
初始状态：当前slot=8，最大可用slot=10，使用率=20%
配置：缩容阈值=30%

决策过程：
1. 使用率20% < 30% → 触发资源闲置缩容
2. 可缩容数量：min(8-1=7, 缩容步长=1) = 1
结果：缩容1个slot
```

#### 场景3：超量运行缩容
```
初始状态：当前slot=5，最大可用slot=1，使用率=88%
配置：缩容阈值=30%

决策过程：
1. 当前5 > 最大1 → 触发超量运行缩容（无论使用率）
2. 可缩容数量：min(5-1=4, 缩容步长=1) = 1
结果：缩容1个slot
```

### 9.9.8 监控指标
建议监控以下关键指标：
1. **资源使用率**：各资源的使用率变化
2. **slot数量**：当前slot数量的变化趋势
3. **扩缩容频率**：扩容/缩容操作的频率
4. **决策延迟**：从检测到调整的时间延迟

### 9.9.9 最佳实践

#### 配置建议
1. **阈值设置**：
   - 扩容阈值：70%-90%（根据业务敏感性）
   - 缩容阈值：20%-40%（保留适当缓冲）
   - 容量阈值：70%-90%（避免过早扩容）

2. **步长设置**：
   - 扩容步长：2-5（避免一次性扩容过多）
   - 缩容步长：1-2（谨慎缩容，避免影响业务）

3. **冷却时间**：
   - 扩容冷却：300-600秒（5-10分钟）
   - 缩容冷却：600-1200秒（10-20分钟，更长以保持稳定）

#### 资源规划
1. **指标选择**：选择最能反映业务压力的资源指标
2. **需求估算**：准确估算每个slot的资源需求
3. **容量预留**：保留20%-30%的缓冲容量应对突发负载

#### 故障处理
1. **资源不足**：系统检测到资源不足时会停止扩容
2. **指标异常**：指标缺失或异常时会跳过该主机
3. **配置错误**：配置解析失败时会使用默认值

### 9.9.10 限制与注意事项

#### 系统限制
1. **指标依赖**：需要完整的三类资源指标
2. **精度限制**：slot数量为整数，可能无法完全匹配资源
3. **延迟性**：从资源变化到调整完成有检查间隔+冷却时间

#### 使用注意事项
1. **避免频繁调整**：合理设置冷却时间和检查间隔
2. **监控告警**：设置关键指标的告警阈值
3. **容量规划**：确保物理资源足够支持最大slot数量
4. **测试验证**：在生产环境前充分测试扩缩容逻辑

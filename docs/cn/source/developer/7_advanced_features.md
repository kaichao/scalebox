## 7.1 容错机制

模块运行错误通常分为两类：
- 逻辑错误：代码逻辑导致的结果错误；
- 非逻辑错误：外部软硬件环境异常导致的结果错误；通常在外部环境恢复后，重复多次运行，可解决；

非逻辑错发生有一定的概率，大规模数据处理中，非逻辑错的自动处理，将大大提升数据处理的效率及可靠性。

### 常见的外部运行环境异常
- 不稳定的硬件和基础软件
  - 网络设备链路的不稳定
  - 环境温度升高，导致计算节点暂时停止服务
  - 磁盘盘阵中介质不稳定，导致RAID暂时失效
  - 集群存储软件的临时性、可修复的bug
- 运行中的随机异常
  - 高负载导致核心存储响应延时增加
    - 可变延时（数秒~几分钟）
    - 暂时性不可写入
  - 高负载导致低概率的内存超分，应用内存不足
  - 系统高负载，不合适的调度策略，导致算法运行超时
- 数据异常
  - 异常输入数据
  - 前导处理软件的随机错误
  - 各类运行异常导致的数据不完整

### 非逻辑错的容错处理
- 系统异常的判断与定位
  - 读取/执行/回写的时间
  - 任务返回码
  - 系统监控的异常信息
- 异常任务的容错处理
  - 自动/人工


### 7.1.1 模块级容错
- 设置module的参数retry_rules。
按照算法代码对于非逻辑错的错误，设置主脚本不同的错误码。按返回错误码，在模块定义中设置自动重试，从而实现自动重试。

在Module定义中，设置```retry_rules```实现以上功能。

```
    retry_rules: "['91','92:3']"
```
在以上设置中，若返回码为91，则重试1次；若返回码为92，则重试3次。

返回码是模块运行的结果代码，模块运行出错的返回码就是错误码。

### 7.1.2 平台级故障及恢复

- slot启动运行出错，但运行task时很快出错，导致task运行时间短，单位时间内可完成多个task；
- module的max_tasks_per_minutes参数（取值>=3），在超出该参数时，将对应slot设置为'ERROR'，以免干扰其他task的正常等待；
- 再结合retry_rules，即可在有大量slot运行错的情况下，停止有问题的slot运行；
- 最后，可以再通过手工恢复。

### 7.1.3 跨模块容错

- 基于vtask
- 在任务中增加用于管理的任务头，实现基于vtask的管理（删除？）
- 清理vtask中设计的task、semaphore、variable等


容错分级
- task级：基于退出码的重试机制。vtask内的task重试，需要调整vtask状态。尽可能在task级恢复。
- slot级：
- vtask级：节点本地计算模式下，保证最终的幂等性。vtask层保持强一致性。
  - vtask内的task，重试，需要调整vtask状态
  - 部分出错（节点退出），只能在vtask级恢复。


## 7.2 准入控制机制

准入控制(Admission Control)

本地计算本地资源受限，需引入准入控制，避免本地节点的关键资源（内存容量、磁盘空间大小）超载。
对于复杂应用程序的本地计算，高级准入控制可大大简化业务逻辑，避免运行异常。

算法模块的准入控制，就是控制流式数据处理的进度，以免数据处理所需不可共享的核心计算资源（内存缓存、GPU显存、本地磁盘空间）超过本地资源的物理限额，导致计算异常中断，包括运行异常退出、程序死锁等。

流量控制的实现机制是在消息处理前，通过模块的标准流控规则、自定义流控规则检查是否符合外部条件，若不符合，则在代码中显式调用sleep()，等待一段时间后再做检查。经过多次检查未果，则退出模块运行。

流控规则通过引入等待机制，降低了局部计算资源的利用率，但从整体上保证应用程序的顺利执行。
避免内存空间的峰值需求，以增加等待时间为代价，在低内存配置的机器上运行本地计算的应用。

流控分为slot级流控、node间并行同步流控。
流控支持模块运行的同步，以免系统资源受限而导致运行异常。

精准控制数据输出，若数据空间不满足，等待其他并行任务完成后释放资源，清理出空间，待空间容量满足要求后再继续运行。

### 7.2.3 vtask计数准入控制

- 标准流控属性```vtask_size```
  - 理解为可运行task的最大数量
  - 若基于vtask框架，在vtask-head模块中，计数器减一，在vtask-tail模块中，计数器加一
  - 若在独立模块中，计数器减一。需在主路由中，手工完成计数器加一操作。

启用vtask的模块，在task启动时将计数器自动减一，若计数器值<=0，则计数流控生效，新task不能运行。从实现上看，vtask机制设置了等待队列长度。

后续模块的任务处理完成后，在主路由中自动恢复vtask计数器。也可对计数器手工操作，实现启停。

- 处理过程
  - 在模块入口处，检查信号量计数器值，若<=0，表示无运行槽位，准入控制不通过；
  - 主路由对该计数值自动减一，占用一个运行槽位。该操作自动完成，不需要编程控制；
  - vtask处理完成，则在对应消息路由中，通过信号量操作，对计数值加一，释放一个空槽位。

## 7.4 超时设置（timeout）

由于代码的bug、数据错误等原因，可能导致算法模块进入死循环，一直占用slot运行，无法正常退出。

超时设置可以解决以上问题。通过设置module的```task_max_seconds```参数，在超出该时限后，该任务（task）会退出运行，返回错误码 124.

在封装脚本调用算法代码时，建议也在封装脚本中加入timeout的相关设置。若无此设置，外层脚本timeout，内层脚本还会运行结束，导致不确定的结果。
若算法代码名为run.py，则封装代码中对应部分可写成：
```sh
timeout ${TASK_TIMEOUT_SECONDS}s run.py $*
```

## 7.7 slot启动命令表达式

支持 `(( ))` 定界符的表达式，在slot启动时，再按外部环境，动态求解表达式，得到最终的启动命令。适用于以下场景：
- 单节点多GPU卡，需通过不同命令启动不同GPU卡对应的slot
- 在准入控制规则中，需以slot序号为变量，精准定义存储容量上限，保证资源充分利用。

### 7.7.1 变量类型

表达式中，变量名用```@```开头，分为数值型变量、字符串变量。

#### 数值型变量（slot序号）
每个模块，针对每个节点，有一个从0计数的序号，可用于slot启动命令表达式，实现对不同slot序号用不同的启动命令。

用 ```@seq```标识计数序号

#### 字符串变量（global变量）
按全局变量值，解析最终slot命令，可指定镜像名版本号

用 ```@v:var_name```标识字符串变量

### 7.7.2 slot序号变量示例

单个计算节点可配置多个GPU加速卡。通常为每个GPU配置独立的slot，模块算法不需针对多GPU卡做并行优化，这样配置通常也更具高运行效率。
在这种场景下，不同GPU需要用不同的slot启动命令。
slot启动命令支持参数化配置。


#### ***应用定义***
```yaml
  beam-make:
    command: ${ROCM_COMMAND}
    arguments:
      free_space_gb: '{"${LOCAL_SHMDIR}":${BEAM_MAKE_FREE_GB}}'
```
#### ***准入控制参数定义***
```env
LOCAL_SHMDIR=/dev/shm/scalebox/mydata
BEAM_MAKE_FREE_GB='((@seq*5+11))'

```
#### singularity多GPU配置命令
```env
ROCM_COMMAND='singularity exec --rocm --env ROCR_VISIBLE_DEVICES=((@seq)) {{ENVS}} {{VOLUMES}} {{IMAGE}} goagent'
```

#### docker多GPU配置命令1
```env
ROCM_COMMAND='docker run -d --rm --network host --tmpfs=/work --device=/dev/kfd --device=/dev/dri --security-opt seccomp=unconfined --group-add video -e ROCR_VISIBLE_DEVICES=((@seq)) {{ENVS}} {{VOLUMES}} {{IMAGE}}'
```

#### docker多GPU配置命令2
```env
docker run -d --rm --network=host --tmpfs=/work --device=/dev/kfd --device=/dev/dri/card((@seq%2)) --device=/dev/dri/renderD((n%2+128)) --security-opt seccomp=unconfined --group-add video --cap-add=SYS_PTRACE {{ENVS}} {{VOLUMES}} {{IMAGE}}
```

## 7.9 slot自动扩缩容

### 7.9.1 概述

Slot 自动扩缩容是 ScaleBox 平台的核心特性之一，用于根据资源使用情况自动调整任务执行槽（slot）的数量。系统通过监控主机资源使用率，智能决策何时扩容（增加slot）或缩容（减少slot），以优化资源利用率和任务执行效率。

### 7.9.2 功能特性

#### 核心功能
- **自动监控**：定期检查主机资源使用情况
- **智能决策**：基于使用率阈值自动决定扩容/缩容
- **双重策略**：支持资源紧张扩容和容量不足扩容
- **安全保护**：防止过度扩容和过度缩容
- **冷却机制**：避免频繁调整，确保系统稳定

#### 扩缩容场景
1. **资源紧张扩容**：当资源使用率超过阈值时扩容
2. **容量不足扩容**：当slot数量远低于最大容量时扩容
3. **资源闲置缩容**：当资源使用率过低时缩容
4. **超量运行缩容**：当slot数量超过物理容量时强制缩容

### 7.9.3 实现原理

#### 系统架构
```
+----------------+     +----------------+     +----------------+
|   资源监控模块   | --> |   决策算法模块   | --> |   Slot调整模块  |
+----------------+     +----------------+     +----------------+
        |                       |                       |
        v                       v                       v
+----------------+     +----------------+     +----------------+
| 收集主机资源数据 |     | 计算扩缩容决策  |     |  执行slot调整   |
+----------------+     +----------------+     +----------------+
```

#### 数据流
1. **资源收集**：从数据库获取主机总资源、已使用资源和slot需求
2. **指标计算**：计算最大可用slot数量和资源使用率
3. **决策判断**：基于阈值判断是否需要调整
4. **执行调整**：通过slot管理接口调整slot数量

### 7.9.4 算法说明

#### 核心算法流程

```go
// 五步算法流程
1. 计算最大可用slot数量
2. 计算最大资源使用率
3. 检查是否需要扩容
4. 检查是否需要缩容
5. 返回调整决策
```

#### 详细算法步骤

##### 1. 计算最大可用slot数量
- 获取总资源、已使用资源、slot需求的交集
- 对每个共同指标：`可用slot = (总资源 - 已使用资源) / slot需求`
- 取所有指标中的最小值作为最大可用slot数量
- 应用配置限制（最小/最大slot数量）

##### 2. 计算最大资源使用率
- 对每个共同指标：`使用率 = 已使用资源 / 总资源`
- 取所有指标中的最大值作为决策依据

##### 3. 扩容检查（双重条件）
- **条件A：资源紧张扩容**
  - 触发：`使用率 > 扩容阈值`
  - 目标：缓解资源压力
- **条件B：容量不足扩容**
  - 触发：`当前slot数量 < 最大可用slot数量 × 容量阈值`
  - 目标：充分利用可用容量

##### 4. 缩容检查（双重条件）
- **条件A：资源闲置缩容**
  - 触发：`使用率 < 缩容阈值`
  - 目标：减少资源浪费
- **条件B：超量运行缩容**
  - 触发：`当前slot数量 > 最大可用slot数量`
  - 目标：强制缩容到物理容量内

##### 5. 调整数量计算
- **扩容数量**：`min(最大可用 - 当前, 扩容步长)`
- **缩容数量**：`min(当前 - 目标, 缩容步长)`
  - 资源闲置缩容：目标 = 最小slot数量
  - 超量运行缩容：目标 = 最大可用slot数量

### 9.9.5 配置说明

#### 启用配置
在模块参数中设置以下配置项：

```json
{
  "autoscaling.enabled": "true",

  "autoscaling.max_slots": "10",
  "autoscaling.scale_up_threshold": "0.8",
  "autoscaling.scale_down_threshold": "0.3",
  "autoscaling.scale_up_step": "2",
  "autoscaling.scale_down_step": "1",
  "autoscaling.scale_up_cooldown_seconds": "300",
  "autoscaling.scale_down_cooldown_seconds": "600",
  "autoscaling.check_interval_seconds": "60",
  "autoscaling.capacity_threshold": "0.8"

```

#### 参数详解

##### 基础参数
| 参数名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `autoscaling.enabled` | boolean | false | 是否启用自动扩缩容 |
| `autoscaling.min_slots` | int | 1 | 最小slot数量（缩容下限） |
| `autoscaling.max_slots` | int | 10 | 最大slot数量（扩容上限） |

##### 阈值参数
| 参数名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `autoscaling.scale_up_threshold` | float | 0.8 | 扩容阈值：使用率 > 此值时扩容 |
| `autoscaling.scale_down_threshold` | float | 0.3 | 缩容阈值：使用率 < 此值时缩容 |
| `autoscaling.capacity_threshold` | float | 0.8 | 容量阈值：当前slot < 最大可用 × 此值时扩容 |

##### 步长参数
| 参数名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `autoscaling.scale_up_step` | int | 2 | 每次最多扩容的slot数量 |
| `autoscaling.scale_down_step` | int | 1 | 每次最多缩容的slot数量 |

##### 时间参数
| 参数名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `autoscaling.scale_up_cooldown_seconds` | int | 300 | 扩容冷却时间（秒） |
| `autoscaling.scale_down_cooldown_seconds` | int | 600 | 缩容冷却时间（秒） |
| `autoscaling.check_interval_seconds` | int | 60 | 检查间隔时间（秒） |

```json
{
  "slot_req.compute_units": "1",

```
该项配置位于模块配置的parameters中。

#### 指标要求
1. **指标一致性**：三类指标需要有相同的key前缀（去掉前缀后）
2. **数值类型**：所有值必须是数值类型（整数或浮点数）
3. **单位一致**：相同指标的单位必须一致

#### 场景1：正常扩容
```
初始状态：当前slot=3，最大可用slot=10，使用率=90%
配置：扩容阈值=80%，容量阈值=80%

决策过程：
1. 使用率90% > 80% → 触发资源紧张扩容
2. 当前3 < 10×80%=8 → 触发容量不足扩容
3. 可扩容数量：min(10-3=7, 扩容步长=2) = 2
结果：扩容2个slot
```

#### 场景2：正常缩容
```
初始状态：当前slot=8，最大可用slot=10，使用率=20%
配置：缩容阈值=30%

决策过程：
1. 使用率20% < 30% → 触发资源闲置缩容
2. 可缩容数量：min(8-1=7, 缩容步长=1) = 1
结果：缩容1个slot
```

#### 场景3：超量运行缩容
```
初始状态：当前slot=5，最大可用slot=1，使用率=88%
配置：缩容阈值=30%

决策过程：
1. 当前5 > 最大1 → 触发超量运行缩容（无论使用率）
2. 可缩容数量：min(5-1=4, 缩容步长=1) = 1
结果：缩容1个slot
```

### 9.9.8 监控指标
建议监控以下关键指标：
1. **资源使用率**：各资源的使用率变化
2. **slot数量**：当前slot数量的变化趋势
3. **扩缩容频率**：扩容/缩容操作的频率
4. **决策延迟**：从检测到调整的时间延迟

### 9.9.9 最佳实践

#### 配置建议
1. **阈值设置**：
   - 扩容阈值：70%-90%（根据业务敏感性）
   - 缩容阈值：20%-40%（保留适当缓冲）
   - 容量阈值：70%-90%（避免过早扩容）

2. **步长设置**：
   - 扩容步长：2-5（避免一次性扩容过多）
   - 缩容步长：1-2（谨慎缩容，避免影响业务）

3. **冷却时间**：
   - 扩容冷却：300-600秒（5-10分钟）
   - 缩容冷却：600-1200秒（10-20分钟，更长以保持稳定）

#### 资源规划
1. **指标选择**：选择最能反映业务压力的资源指标
2. **需求估算**：准确估算每个slot的资源需求
3. **容量预留**：保留20%-30%的缓冲容量应对突发负载

#### 故障处理
1. **资源不足**：系统检测到资源不足时会停止扩容
2. **指标异常**：指标缺失或异常时会跳过该主机
3. **配置错误**：配置解析失败时会使用默认值

### 9.9.10 限制与注意事项

#### 系统限制
1. **指标依赖**：需要完整的三类资源指标
2. **精度限制**：slot数量为整数，可能无法完全匹配资源
3. **延迟性**：从资源变化到调整完成有检查间隔+冷却时间

#### 使用注意事项
1. **避免频繁调整**：合理设置冷却时间和检查间隔
2. **监控告警**：设置关键指标的告警阈值
3. **容量规划**：确保物理资源足够支持最大slot数量
4. **测试验证**：在生产环境前充分测试扩缩容逻辑

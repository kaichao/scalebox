# 1. 核心概念

## 1.1 从大规模计算到 Scalebox 应用

超大规模科学计算无法由单个算法一次完成：必须把大问题分解为若干可并行、相互协作的算法；每个算法封装为模块，模块内的 task 不持有应用状态，平台可以按需调度、重试、迁移。

节点本地计算让单个 task 尽量在节点内完成数据读写，解决“快不快”的问题；但局部最优不等于全局正确。多个模块之间需要按数据关系协作：谁先算、谁后算、结果交给谁、何时汇总。这就是**并行逻辑**，由**主路由模块**执行。

主路由执行并行逻辑、读写应用状态、分发任务、组织模块协作。如果主路由只做最简单的任务分发，Scalebox 就退化为一个常见的工作流引擎；主路由的价值在于把任务分发提升为对计算过程的持续管理。

```text
大问题
  → 并行逻辑：分解为小问题/任务
  → 算法逻辑：模块内计算小问题
  → 应用状态：记录进度、分组、配额
  → 主路由：执行并行逻辑、分发任务、更新状态
  → 协作式调度持续推进，直到应用目标完成
```

## 1.2 概念分层

### 1.2.1 基本概念：应用结构与资源结构

Scalebox 的基本概念分两组：

| 分组 | 概念 | 说明 |
|---|---|---|
| 应用结构 | App（应用） | 完成特定计算任务的应用程序，由 `app.yaml` 定义，包含多个 Module |
| 应用结构 | Module（模块） | 容器化封装的算法或功能单元；类型包括算法、传输、路由、辅助 |
| 应用结构 | Task（任务） | 输入数据在具体 Module 上的执行实例；有 body、headers 与唯一 ID |
| 资源结构 | Cluster（集群） | 计算资源的逻辑分组；支持单节点、静态、动态（外部调度器，如 Slurm）、内联等类型 |
| 资源结构 | Host（节点） | 执行计算任务的服务器节点 |
| 资源结构 | Slot（运行槽） | 节点上与 Module 对应的资源切片，是 Task 细粒度调度的基础单位 |

关系可以简化为：

```text
App → Module → Task
Cluster → Host → Slot
```

- App 由多个 Module 组成；Module 接收 Task。
- Cluster 包含多个 Host；Host 上创建多个 Slot；Task 在 Slot 中执行。
- App/Module/Task 描述“应用由什么构成”；Cluster/Host/Slot 描述“计算资源如何组织”。

### 1.2.2 编程原语：状态与通信

平台提供一组底层编程原语，是应用状态与跨应用/跨集群信息共享的实现基础：

- **状态原语**：semaphore（信号量）、semagroup（信号量组）、variable（共享变量）、global（全局变量）。
- **通信原语**：queue（队列）。
- `global` 同一物理集群内跨应用；`queue` 跨物理集群。
- 这些是“编程相关的基本概念”，属于平台底层支持；核心概念（见 §1.2.3）建立在其上。

完整的作用域、用途与命令见 §1.10。

### 1.2.3 核心概念：3+1

核心概念采用“3+1”：

- **概念三角**：计算逻辑、应用状态、主路由。
- **封装载体**：VTask。

```text
计算逻辑
├─ 算法逻辑（模块内）—— 模块执行
└─ 并行逻辑（模块间）—— 主路由执行
应用状态 —— 主路由读写，平台存储
主路由 —— 应用控制面
VTask —— 跨模块协作与状态的粗粒度封装
```

- **计算逻辑**是规则：描述整个计算过程中的逻辑关系。
- **应用状态**是记忆：记录进度、分组、配额，支撑计算逻辑持续推进。
- **主路由**是执行者：执行并行逻辑、读写应用状态、分发任务、组织协作。
- **VTask** 是封装：把跨模块的零散 task 组织为粗粒度计算单元，承载其状态、流控、资源绑定与容错。

## 1.3 计算逻辑

**计算逻辑 = 算法逻辑 + 并行逻辑**。它是应用级总概念，描述整个计算过程中的逻辑关系：

- **算法逻辑**（模块内）：回答“一个小问题怎么算”。
- **并行逻辑**（模块间）：回答“大问题怎么分解、分解后怎么协作”。

“应用逻辑”与计算逻辑同义；本文统一使用“计算逻辑”。

### 1.3.1 算法逻辑（模块内）

算法逻辑是模块内部的算法实现逻辑，包括算法步骤、数据结构、模块内并行（多线程、GPU）等。

- 由算法模块实现；平台和主路由不感知其内部细节。
- 主路由只看到 task 的输入输出与消息，不执行算法逻辑。
- 模块内并行属于算法逻辑，不属于并行逻辑。

例：分片求和中的 `worker` 计算部分和、`collector` 合并结果，都是算法逻辑。

### 1.3.2 并行逻辑（模块间）

并行逻辑是模块之间的组织逻辑，回答“大问题怎么分解、分解后怎么协作”，包括：

- **问题分解**：把大计算问题拆成小问题/任务。
- **任务分发**：把任务送到对应模块与 slot。
- **分组与排序**：哪些数据一起算，按什么顺序算。
- **同步与汇聚**：何时等待、何时合并结果。
- **流控与准入**：并发度、配额、资源绑定。
- **模块级并行与模块间并行**：同一模块多实例、流水线并行。

并行逻辑由主路由执行。它不包含模块内部的算法步骤，也不包含模块内并行（线程/GPU，那属于算法逻辑）。平台负责资源与 slot 调度，主路由负责应用级任务编排。

并行逻辑的载体包括：

- `app.yaml` 中的模块与拓扑定义。
- 主路由脚本中的分支、循环与任务生成逻辑。
- 任务头（`_` 前缀）与任务体中的控制字段。

实现细节见 {doc}`主路由与应用状态 <../developer/4_main_router_status>`。

## 1.4 应用状态

**应用状态**是应用级、跨 task/跨 module、保存在平台存储中的控制状态，用于支持并行逻辑持续推进。

内容包括：

- **进度与计数**：已完成分片数、在制任务数、剩余数量。
- **阶段**：当前处于加载、计算、回写、汇总中的哪一步。
- **分组**：哪些数据属于同一组，组内进度。
- **配额**：并发上限、准入配额、资源绑定。
- **游标与配置**：下次处理位置、运行期参数。

应用状态不是业务数据、不是结果文件、不是日志。

**为什么需要**：

- task 是执行实例，无应用状态；module 是无状态算法。
- 无状态才能让平台任意调度、重试、迁移 task。
- 应用整体必须有记忆，否则无法知道“做到哪了、下一步做什么”。

**平台存储与通信原语**：

- **semaphore（信号量）**：计数、配额、进度；如 `vtask_size`、`node_progress`。
- **variable（共享变量）**：应用内字符串状态；如阶段、游标、配置。
- **global（全局变量）**：同一物理集群内跨应用共享的信息/配置。
- **queue（队列）**：跨物理集群的管理面消息共享，不属于应用内状态存储。

**传递机制**：

- **任务头**：`_` 前缀 header 随任务自动传播，把状态从主路由带到算法模块再带回。
- **VTask**：把跨模块 task 串成一条计算链，平台自动维护其生命周期与资源信号量。

**读写纪律**：

- **应用层**：主路由集中写，避免应用层并发冲突。
- **平台层**：controld 也会读写信号量，例如 vtask 的 bind 预扣、gate 扣减、tail 完成归还；这些操作由平台层统一处理，避免应用层可能出现的并发访问问题。
- **算法模块**：通常只读，用于准入控制或分支判断。
- vtask 资源信号量由平台自动维护，脚本只做 bind/unbind 或 gate 操作。

**生命周期**：应用创建时初始化，任务推进时更新，应用删除时清理；global 在同一物理集群内跨应用持久。

**与容错的关系**：状态在平台，task 失败可重试或迁移；vtask 在跨模块层保证幂等与最终一致。

## 1.5 主路由模块

**主路由模块（main-router）** 是应用的控制面模块，执行并行逻辑、读写应用状态、分发任务、组织模块协作。

**职责**：

1. **执行并行逻辑**：根据回流消息与当前状态，决定下一步生成哪些任务、发往哪个模块。
2. **读写应用状态**：集中维护进度、计数、阶段、配额等控制状态。
3. **分发任务**：把任务发往算法模块或基础模块，并携带必要的任务头。
4. **组织协作**：把多个模块串成完整计算过程，直到应用级目标完成。

**边界**：

- 不是平台控制面；平台控制面是 controld/actuator。
- 不管理容器、节点与 slot；这些由平台负责。
- 不执行算法逻辑；算法在算法模块内完成。
- 不持有业务数据；业务数据通过任务体、文件或消息传递。
- 不是消息总线，也不是 API 网关。

**运行形态**：

- 运行形态上是应用中的一个模块（容器/脚本），功能上是应用控制面。
- **原则上单实例**：逻辑串行，避免并发写应用状态。
- **高负载例外**：可按模块分设独立主路由实例，使用 `task_dist_mode: SLOT-BOUND` + 多 slot；源模块通过 `router_index` 指定实例。
- **并发正确性由程序员保证**：采用多实例时，应用作者必须确保同一信号量/共享变量不会被多个主路由实例并发写；平台不提供跨实例的自动互斥。
- 可用 bash、Go、Python 等语言实现。

示例（app-mwa 的 beam-form 管道）：

- `router-beam-form`：`task_dist_mode: SLOT-BOUND`，`slots: h0:3`，即 3 个主路由实例。
- `pull-unpack`：`router_index: 2`；`beam-make`：`router_index: 1`；其余模块使用默认实例。
- 这样把 task 数量较多的模块分流到独立实例，同时每个状态变量仍只由一个实例写。

**与传统并行计算框架的区别**：

- 传统框架中，并行逻辑通常嵌在运行时或主程序里；Scalebox 把并行逻辑上移为一个可编程、可替换的主路由模块。
- 平台负责资源与 slot 调度；主路由负责应用级任务编排。
- 并行逻辑因此可见、可测、可容错。

**为什么不是工作流引擎**：

- 如果主路由只做最简单的任务分发，Scalebox 就退化为一个常见的工作流引擎。
- 工作流引擎通常按静态 DAG 调度任务，不负责应用级状态、跨模块协作、准入控制与节点本地计算。
- 主路由的价值在于：执行动态并行逻辑、读写应用状态、组织模块协作，把“任务分发”提升为“计算过程的持续管理”。

**为什么需要**：

- 算法模块无状态且彼此不感知；没有全局协调者，就无法表达跨模块依赖、汇聚与进度。
- 主路由只处理粗粒度控制消息，数据搬运与计算在模块内并行完成，因此串行协调不会成为性能瓶颈。

**常见误解**：

- “主路由是平台组件” → 错。它是应用定义中的一个模块，功能上是应用控制面。
- “主路由执行整个计算逻辑” → 错。它执行并行逻辑；算法逻辑在模块内。
- “主路由处理业务” → 错。它处理控制流，不处理业务算法。
- “主路由必须单实例” → 准确说法是“原则上单实例”；高负载下可按模块分设多实例，但必须保证状态写入不重叠。

## 1.6 VTask

**VTask（虚拟任务）** 是对计算逻辑中跨模块协作部分（并行逻辑）及其状态的粗粒度封装。

它做什么：

- 把零散 task 组织为一个计算单元（分组）。
- 内建/封装 vtask 作用域的状态、流控、资源绑定与容错。
- 直接支持流控、容错，提升可管理性。

它不做什么：

- 不封装算法逻辑；算法仍在各模块内。
- 不是独立调度器；调度由平台与主路由完成。
- 全局变量是同一物理集群内跨应用配置，不属于 vtask 作用域；vtask 主要使用 vtask 作用域的信号量/变量和资源信号量。

三种模式：

| 模式 | 资源绑定 | 管道结构 | 适用场景 |
|---|---|---|---|
| DEFAULT | 无 | task → vtask-head → vtask-core → vtask-tail | 轻量批处理 |
| HOST-BOUND | 单节点 | task → wait-queue → vtask-head → vtask-core → vtask-tail | 单节点独占计算 |
| GROUP-BOUND | 节点组 | task → wait-queue → vtask-head → vtask-core-1 → ... → vtask-tail | 多节点协同计算 |

VTask 是“3+1”中的“+1”：建立在计算逻辑、应用状态、主路由三角之上的第一类封装。完整设计见 {doc}`VTask 虚拟任务 <../developer/9_vtask>`。

## 1.7 核心概念如何协作

### 1.7.1 闭环

一句话：**主路由执行并行逻辑，模块执行算法逻辑，应用状态提供记忆，VTask 提供粗粒度封装。**

闭环：

1. 主路由读取应用状态。
2. 主路由按并行逻辑判断下一步。
3. 主路由生成任务并分发。
4. 算法模块执行算法逻辑，返回消息。
5. 主路由根据结果更新应用状态。
6. 回到第 1 步，直到应用目标完成。

```text
大问题
  → 并行逻辑（主路由）：分解、分发、同步、汇聚
  → 算法逻辑（模块）：计算小问题
  → 应用状态（平台存储）：记录进度、分组、配额
  → VTask：把跨模块 task 封装为粗粒度计算单元
```

### 1.7.2 分片求和的示意

场景：分片求和。模块为 `main-router`、`worker`、`collector`。

**并行逻辑**：

1. `main-router` 把 N 个分片任务发给 `worker`。
2. 所有分片完成后，触发 `collector` 汇总。

**算法逻辑**：

1. `worker` 计算每个分片的部分和。
2. `collector` 合并部分和。

**应用状态**：

- `semaphore pending = N`：剩余分片数。
- `semaphore ready = 0`：已完成分片数。
- `variable stage = "compute" / "aggregate"`：当前阶段。

**主路由**：

- 初始：读取 `pending`，生成 N 个 `worker` task。
- 每个 `worker` 完成：`ready +1`，`pending -1`。
- `pending == 0`：`stage` 置为 `aggregate`，生成 `collector` task。
- `collector` 完成：应用目标完成。

**VTask 视角**：可以把每个分片的 `worker → collector` 链封装为一个 vtask，由 vtask 承载该链的状态、流控与容错；本例不展开。

示例是示意，不对应仓库中的具体应用。

## 1.8 无状态与有状态

### 1.8.1 task 无应用状态

Task 是一次执行实例，携带本次输入（body/headers）与唯一 ID，但不携带应用级进度。Task 可以失败重试、迁移到其他 slot，而不会丢失应用状态。

### 1.8.2 module 无状态

Module 是无状态算法：容器内不保存跨任务的持久状态；同一 task 可以重复执行（幂等由模块或 vtask 层保证）。

- 模块通过环境变量、任务头定义不同逻辑处理。
- 模块内并行（线程/GPU）属于算法逻辑，不属于应用状态。
- 模块可以读取应用状态（如信号量）用于准入控制或分支判断。

### 1.8.3 应用状态在平台存储

应用状态不保存在模块内存中，而保存在平台存储（semaphore/variable/global）与 vtask 生命周期中。主路由集中读写；平台 controld 在 vtask 等场景也会读写；算法模块通常只读。

这样做的结果：

- Task 可以任意调度、重试、迁移。
- 应用整体仍然“记得”进度、分组与配额。
- 失败恢复可以在 task 级或 vtask 级完成。

## 1.10 编程原语详解

平台编程原语分两类：

- **状态原语**：semaphore、semagroup、variable、global。
- **通信原语**：queue。

| 原语 | 作用域 | 用途 | 存储 / 命令 |
|---|---|---|---|
| semaphore（信号量） | app 或 vtask | 计数、流控、准入、进度同步 | `t_semaphore`；`scalebox semaphore` |
| semagroup（信号量组） | 组内信号量（app/vtask） | min/max/diff 等组操作，多节点/多通道同步 | `scalebox semagroup` |
| variable（共享变量） | app 或 vtask | 字符串状态：阶段、游标、配置 | `t_variable`；`scalebox variable` |
| global（全局变量） | 同一物理集群内跨应用 | 跨应用共享信息/配置 | `t_global`；`scalebox global` |
| queue（队列） | 跨物理集群 | 管理面消息共享 | 目标集群数据库；`scalebox queue` |

要点：

- `semagroup` 不是独立存储，是信号量的组视图/批量操作。
- `global` 只在同一物理集群内跨应用；跨物理集群使用 `queue`。
- `queue` 不是 wait-queue，也不是平台内部任务队列；消息存放在目标集群数据库，`--cluster` 选择远端，出队顺序 priority DESC、id ASC；支持 `ls / peek / pull / purge / push`。
- 编程原语是平台底层支持，不等同于核心概念；应用状态与跨应用/跨集群协作建立在其上。

## 1.11 并行化方式

按“计算逻辑 = 算法逻辑 + 并行逻辑”分类：

### 算法逻辑内：模块内并行

算法内部的代码级并行，如多线程、GPU 加速。由算法模块实现；平台与主路由不感知。

### 并行逻辑内：模块级并行与模块间并行

- **模块级并行**：同一模块的多个实例并行处理不同数据，实现数据并行。
- **模块间并行**：不同模块通过流水线方式并行执行，实现流水线并行。
- **混合并行**：结合以上方式，实现最优并行效率。

详细策略见 {doc}`编程模型 <../developer/1_programming_model>` §1.7。
